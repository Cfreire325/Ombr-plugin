# Ombr Studio Creator - Figma Import Strategy

## Future role of the Figma plugin

The Figma plugin should progressively become a focused importer and synchronizer. The web app is the primary interface for creating and editing the design system.

In V1, the plugin should:

- Accept an import key or link generated by the web app.
- Resolve or receive TokenBundle data.
- Import tokens into Figma.
- Create variables.
- Create collections.
- Create modes.
- Preserve aliases where possible.
- Report sync completion or failure.

## Import by key or link

The user flow shows a Figma import key. The exact transport remains an open product/technical question:

- Local key: simple for local MVP, but limited for cross-device use.
- File-based payload: explicit and inspectable, but less smooth.
- Remote key or link: better long-term handoff, but requires hosted storage and security rules.

V1 should keep the concept simple: the web app generates a handoff value, the plugin accepts it, and the user understands what will be imported.

## TokenBundle to Figma variables

TokenBundle is the source. Figma variables are the target representation.

The adapter should map:

- Color tokens to Figma color variables.
- Typography-related token data only where supported by the chosen Figma strategy.
- Spacing, radius, width, and container values to compatible variable types.
- Semantic aliases to Figma variable aliases where supported.
- Light and dark values to Figma modes.

## Collections and modes

The V1 flow requires the plugin to create collections and modes. The default mapping should preserve the user's project mode choices:

- Light only creates a light mode.
- Dark only creates a dark mode.
- Light + Dark creates both modes.

Collections should be organized around token usage in a way that remains understandable in Figma. The exact collection split should follow the TokenBundle structure and naming convention.

## Alias handling

Semantic tokens should keep references to primitive tokens where possible. This allows Figma users to see relationships between base values and semantic usage.

Risks:

- Some aliases may not map cleanly to Figma variable types.
- Missing aliases must be detected before import.
- Circular references must be rejected.
- Mode-specific aliases must resolve consistently for light and dark modes.

## V1 one-way strategy

V1 sync is one-way: web app -> Figma.

The flow is:

1. User creates or edits a project in the web app.
2. User generates a Figma import key.
3. User opens the Figma plugin.
4. User pastes the key.
5. Plugin imports TokenBundle data.
6. Plugin creates variables, collections, and modes.
7. Project is marked as connected.
8. Sync status is updated.

This avoids bidirectional merge complexity in V1.

## V2 bidirectional strategy

V2 may support:

- Import from Figma.
- Pull Figma -> web app.
- Bidirectional sync.
- Difference checks.
- Conflict resolution.

These features require Figma reads, source metadata, revision tracking, diffing, and user-visible conflict decisions.

## Conflict risks

Conflicts appear when both the web app and Figma can change the same token. Examples:

- Token renamed in the web app and edited in Figma.
- Light value changed in one tool and dark value changed in the other.
- Alias changed in Figma but primitive deleted in the web app.
- Collection or mode structure changed manually in Figma.

V1 avoids these by keeping the web app as source of truth.

## Why the plugin should stay simple

The plugin runs in a constrained Figma environment. It should not become the full product interface again.

Keeping it simple reduces:

- Runtime complexity.
- UI duplication.
- Type duplication.
- Sync risk.
- Maintenance cost.

The plugin should rely on `ds-core` and `figma-adapter` rather than owning product logic.

## Dashboard sync status

The dashboard should expose sync status in simple terms:

- Not connected.
- Import key generated.
- Connected.
- Synced.
- Sync available.
- Sync failed.
- Last synced timestamp, when available.

V2 may add:

- Differences available.
- Conflict detected.
- Pull available.
- Needs resolution.

## Safe sync feedback UI states

The validated visual direction requires Figma sync to feel safe and transparent. V1 sync states should be explicit and quiet, not flashy or magical.

Suggested UI states:

| State | Meaning | User-facing behavior |
| --- | --- | --- |
| Empty / not connected | The project has no Figma connection yet. | Show a clear action to generate an import key. |
| Import key generated | A handoff value exists but the plugin has not confirmed import. | Show next steps: open plugin, paste key, import tokens. |
| Loading / importing | The plugin or web app is processing import/sync. | Show progress text tied to real steps: importing tokens, creating variables, creating collections/modes. |
| Connected | The project has been linked to a Figma import. | Show connection status and last known sync metadata. |
| Synced | Last push web app -> Figma completed. | Show a calm success state with timestamp if available. |
| Sync available | Web app data changed after the last sync. | Show a clear push action, not an alarming warning. |
| Failed | Import or sync failed. | Show the failed step and recovery action. |
| V2 conflict | Web app and Figma diverged. | V2 only; show comparison and resolution choices. |

The dashboard should summarize sync state. The Creator workspace can show more detail near export/sync controls.

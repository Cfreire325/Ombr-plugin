# Ombr Studio Creator - Product Vision

## Product definition

Ombr Studio Creator is a web app for building design systems. It lets users create, organize, preview, export, and synchronize the foundations of a design system from one primary interface.

Ombr Studio Creator is a design system builder that lets users create a design system once, then export it to Figma and code.

## Why move from a Figma plugin to a web app

The current Figma plugin is useful for creating design tokens inside Figma, but the product flow now points to a broader system: a standalone creator where users can manage projects, presets, modes, previews, exports, and sync state.

A web app is better suited for:

- A public landing page and product onboarding.
- Guest mode and future authenticated accounts.
- A dashboard with multiple projects.
- Guided project creation.
- Rich token editing and preview.
- Developer exports such as JSON, CSS variables, and Tailwind config.
- Future team workspaces, GitHub sync, version history, documentation, and advanced exports.

The plugin remains important, but it should no longer carry the whole product experience.

## Role of the web app

The web app is the main product surface. In V1, it owns the creation and editing loop:

- Discover the product.
- Start as guest or signed-in user.
- Create or open a local project.
- Configure foundations: colors, typography, spacing, and radius.
- Define primitive and semantic tokens.
- Preview light and dark modes.
- Export to JSON, CSS variables, and Tailwind config.
- Generate a Figma import key.
- Push the web app source of truth into Figma.

## Role of the Figma plugin

The Figma plugin progressively becomes an importer and synchronizer. In V1, its expected role is intentionally narrow:

- Receive an import key or equivalent handoff from the web app.
- Import the TokenBundle generated by the web app.
- Create Figma variables.
- Create collections and modes.
- Update sync status.

The plugin should stay simple so that Figma-specific runtime constraints do not shape the whole product architecture.

## Product promise

The promise is to make design system creation approachable without trapping the user inside one tool. A user should be able to create a system once, inspect it visually, and then deliver it to both design and code surfaces.

For designers, Ombr reduces the friction of setting up coherent foundations and semantic tokens. For developers, it produces predictable exports. For teams, the longer-term promise is a shared source of truth that can sync with Figma and code workflows.

## Target users

- Product designers who need a fast, guided way to create design system foundations.
- Design system designers who need editable tokens, modes, and previews.
- Frontend developers who need JSON, CSS variables, or Tailwind config outputs.
- Small teams that need a practical bridge between Figma and implementation.
- Future teams that need workspaces, GitHub sync, version history, and documentation.

## V1 positioning

V1 is a focused foundation builder, not a complete design system platform. It should feel useful without a full account and should make the first successful project easy:

- Create a project.
- Generate foundations.
- Edit token tables.
- Preview results.
- Export developer artifacts.
- Import into Figma through the plugin.

V1 should avoid billing, teams, bidirectional sync, conflict resolution, full component generation, and advanced documentation.

## Relationship to the validated UI direction

The visual direction supports the product strategy. Ombr Studio Creator should feel like a mix of Figma Variables, Linear, and Storybook:

- Figma Variables for structured token tables and clear light/dark values.
- Linear for navigation clarity, density, hierarchy, and polished tool surfaces.
- Storybook for later component preview logic, not for V1 component-builder scope.

The UI should feel clean, premium, structured, and useful. Premium quality should come from precision, spacing, hierarchy, readable token editing, safe export states, and transparent Figma sync feedback.

The visual direction must not redefine the product roadmap. It should not push V1 into decorative SaaS pages, flashy motion systems, advanced component builders, or generic AI-style visuals.

## Long-term vision

The long-term product can grow into a full design system operations layer:

- Team workspaces.
- Import from Figma.
- Bidirectional sync.
- Conflict resolution.
- GitHub sync.
- Style Dictionary advanced outputs.
- React theme export.
- Component builder and variants.
- Storybook-like preview.
- Version history.
- Auto documentation.
- Advanced accessibility checks.

The long-term direction should build on the V1 source-of-truth model instead of replacing it.
